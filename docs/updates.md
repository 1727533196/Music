# 在线更新（Windows x64）

使用公开的 GitHub Releases 托管完整安装包，不需要新增后端服务。客户端默认读取：

`https://github.com/1727533196/Music/releases/latest/download/version.json`

这条链路使用自定义安装器的更新模式，与 electron-builder 生成的 NSIS `latest.yml` 无关。客户端不包含 GitHub Token；私有仓库的下载不在本实现范围内。

## 构建与发布

1. 将根目录 `package.json` 和 `installer/package.json` 的版本号改为相同的正式版本，例如 `1.0.2`。每次发布必须递增版本号。
2. 确认 `../NeteaseCloudMusicApi/bin/ncm-server.exe` 已存在。需要更新该服务时先运行 `pnpm server:build:win`。
3. 在 Music 目录运行 `pnpm update:build:win`，构建主程序、安装器并自动生成 `dist/installer/version.json`。首次接入必须完整构建，不能复用不含更新功能的旧主程序。
4. 添加更新说明：`pnpm update:manifest --notes "本次更新说明"`，也可用 `--notes-file 路径` 读取 UTF-8 文本。
5. 在 GitHub 创建版本对应的 Release（例如标签 `v1.0.2`），上传 `dist/installer/install-win.exe` 和 `dist/installer/version.json` 两个附件。先传完附件，再发布为 **Latest 正式版本**；草稿和 prerelease 不会成为这条地址的最新版本。

`install-win.exe` 是构建脚本生成的发布副本，沿用仓库现有附件命名，与本地的 `Tinglan-安装包.exe` 内容一致。请保持发布附件名不变，清单里的版本号、下载地址和校验值必须对应同一份安装包。

如果只修改安装器而主程序产物仍是当前版本，可用 `pnpm --dir installer pack:win`；它也会重新生成更新信息。生成脚本会检查被打包的主程序版本和更新入口，防止发布旧程序。

换仓库时生成信息可加 `--repo owner/repo`，同时设置客户端运行环境变量 `MUSIC_UPDATE_URL` 为新仓库的清单 HTTPS 地址。未指定时始终使用上方默认地址。公开更新文件也可以改放普通 HTTPS 静态服务器；保持清单字段一致即可。

更新文件地址需支持 HEAD 请求，重定向全程使用 HTTPS。

## 下载加速与自动切换

GitHub 安装包默认先尝试 `https://gh-proxy.org/` 加速，再尝试 GitHub 直连。自有下载服务器的地址仍优先使用。下载页会显示当前来源和实时速度。

- 连接超过 12 秒、15 秒没有收到数据，或连续 30 秒下载不足 1 MiB，会切换到下一个来源。
- 每个来源都验证完整的文件大小及 SHA-256，错误页面、损坏文件和不安全的重定向都会被放弃。
- 如果所有可用来源都较慢，会按刚才测得的速度排序，放宽最低速度限制后重试；无数据超时限制仍然保留。
- 切换来源会重新下载该文件，进度可能归零；目前没有跨来源断点续传。取消会停止整个下载过程并清理临时文件，不会继续请求备用来源。

公共加速服务的可用性随网络和服务状态变化，不能保证固定速度。默认源使用规范见 [GH-Proxy 文档](https://gh-proxy.com/docs/github-accelerator)。

可以在生成清单时配置自有下载地址和额外备用地址，无需修改客户端代码：

```powershell
pnpm update:manifest --download-url "https://downloads.example.com/1.0.2/install-win.exe" --mirror "https://backup.example.com/1.0.2/install-win.exe" --notes "本次更新说明"
```

`--mirror` 可重复传入，最多 8 个，写入清单的 `mirrors` 数组。每个地址必须提供同一份安装包。GitHub 主地址的显式备用地址会优先于内置加速源使用，最后保留 GitHub 直连；自有主地址始终排在首位。安装包内容不变时，校验值无需因更换服务器而修改。

客户端也支持运行环境配置：

| 变量                   | 格式与作用                                                                                                                                  |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `MUSIC_UPDATE_MIRRORS` | HTTPS 加速前缀的 JSON 数组，例如 `["https://gh-proxy.org/"]`；设置为 `[]` 可关闭自动添加的加速源。清单显式指定的主地址和备用地址仍会使用。 |
| `MUSIC_UPDATE_URLS`    | 可信版本清单完整地址的 JSON 数组，按顺序尝试；优先于单个 `MUSIC_UPDATE_URL`。每个来源最多等待 12 秒，失败、404 或清单格式错误会尝试下一个。 |

默认版本清单仍通过 GitHub 原地址读取，不自动交给公共代理。清单包含版本和安装包校验依据，额外清单地址应由发布者控制并保持同步。旧版本不包含自动选源逻辑，需要升级到新的客户端后生效。

为了让旧版下载首次升级包时也能使用加速，可在生成清单时将 `--download-url` 指向加速后的完整 GitHub 地址，同时用 `--mirror` 保留 GitHub 原地址。旧版只会使用主 `url`，新版才会自动切换来源。更换下载地址不改变安装包本身及其校验值。

## 用户体验与文件保留

- 已安装的 Windows x64 应用启动 15 秒后检查一次；“设置 → 通用与关于 → 应用更新”可手动检查。
- 发现新版仅提示，不自动下载或中断播放。下载支持进度、取消和重试，并验证文件大小及 SHA-256。
- 点击“重启更新”后，先启动独立安装器并等它确认就绪，再退出主程序。取消 Windows 权限提示或启动失败时，原应用继续运行。
- 安装器等待原应用退出，只停止原安装目录下的程序和本地服务。新文件在同一磁盘暂存，旧文件先备份；替换失败会恢复旧文件。`data/`、已有卸载入口、服务配置、快捷方式和启动选项保留，已安装的服务程序随包更新。
- 更新期间磁盘应能额外存放一份解压后的主程序。程序退出、权限确认、网络或磁盘故障会显示错误，可重试。断电或系统终止安装器时不承诺自动恢复，可用完整安装包修复；错误中标出的备份目录应保留。
- macOS、Linux 和浏览器预览暂不支持安装更新；开发模式仅供检查远端版本。
- 当前没有更新模块的旧版本需要先手动安装一次新包。

## 验证真实发布链路

准备两个递增版本：先手动安装带更新模块的低版本，再将高版本的两个附件发布到 Release。检查更新、下载、取消后重试、拒绝权限后重试、重启更新，确认版本变更、原安装位置和登录状态均保留。网络失败或尚无 Release 时应显示相应状态。

GitHub 地址规则：[GitHub 官方文档](https://docs.github.com/en/repositories/releasing-projects-on-github/linking-to-releases)。普通 Git 推送不会生成或发布 Release。
